## 任务执行原则

先产出一条完整、正确且可复现的「程序 → 多阶段 IR → native binary → 正确性 → 多次计时 → 结构化记录」路径，再增加程序和变换。优先使用现有 MLIR/LLVM 工具；尽量用 Python 负责组织与采集，不为了调度实验就新写 C++ Pass。

所有新增实现需能在仓库内直接运行，任何假设性 CLI 示例应替换为测试通过的真实命令。只保留必要依赖。不要自行启动大规模 GPU / NPU 训练、下载庞大模型、部署集群或改造 LLVM 源码。

## M0：环境侦测与最小可用编译链

首先检查本机系统、CPU 架构和 MLIR/LLVM 安装情况，确认 `mlir-opt`、`mlir-translate`、`clang`/`llc`、`llvm-config` 等具体工具的版本与可用 Pass。若未安装 MLIR，提供最短可执行安装说明或轻量替代方案；不要默认可以构建 LLVM 全家桶。切忌使用不存在的 Pass 参数。

**第一笔实现提交应做到：**
1. 一个非常小的 MLIR 样例（如向量/矩阵运算中的一项）以及参考结果和运行器；
2. 一条在当前环境经过实际执行的、从 MLIR 编译为本机可执行文件的 Pipeline；
3. 保存输入 IR、至少一个中间 IR、LLVM IR、最终产物及构建日志；
4. 自动验证输出正确性，实测多次执行延迟；
5. 采集主机、工具链、执行命令等元数据，生成一条包含成功或失败状态的机器可读记录；
6. 简短记录实际使用的命令与遇到的版本限制。

如环境不允许安装工具链，先提交探测脚本、精确的依赖说明和可运行的纯本机环境测试，不要声称编译闭环已验证。

## M1：可重复的候选与性能采集

把 M0 的手工操作收敛为可配置的实验入口。建议支持以下功能，而不是拘泥于文件名：

- `probe`：机器 / 工具链信息探测；
- `compile`：对指定 Case + Pipeline 生成各阶段快照和二进制；
- `run`：正确性与计时；
- `collect`：批量组织候选与生成 JSONL 记录；
- `summarize`：聚合运行样本与输出候选排名。

可选接口例如 `python -m irloom.collect --config experiments/phase0.yaml`，**这只是期望接口，不代表仓库已有该命令**。实现后在 README 或专门运行指南中写入经过实测的真实命令。

先让一个 Case 至少两条不同合法编译路径完成端到端测量，确认两条路径的 IR 快照、优化事件、编译命令和产物哈希各自可追溯，并用多次测量区分可能的噪声。不要将“Pass 列表不同”直接视为“实现不同”。

## M2：扩充小型工作负载矩阵

按 [PHASE0_PROTOCOL.md](PHASE0_PROTOCOL.md) 扩展到计算密集、归约、访存/数据复用三类程序，每类先两个输入规格，并逐步引入四条有意义的合法变换轨迹。候选可以因工作负载而不同，**不要求所有类别强行套同一组 Pass**。工具链不支持时应明确输出失败类型、候选缺失以及建议替代路径。

对每类程序保留一个独立参考实现，包含精度阈值和非法候选剔除逻辑；加基础回归测试，确保数据 schema、编译产物、哈希引用、计时单位一致。

## M3：第一轮证据分析

输出 `experiments/reports/phase0-initial.md`（首批）及一个简明汇总文件，回答：

1. 哪些 Case 的合法路径呈现超出噪声的最终性能差异？不同优化阶段的决策如何影响这些路径？
2. 是否能稳定取得高、中、低抽象阶段的快照和准确的变换历史？在哪些 Pass 上丢失了可追踪关系？
3. 哪些性能变化可以通过明确的受控实验解释？哪些还只是相关性？
4. 若时间允许，在固定决策检查点试做「当前 IR」vs「当前 IR + 上游信息」的极简排名模型。严格避免未来信息泄漏，报告数据不足造成的限制。

重要：如果初期只有 20–50 条有效样本，可以只做描述统计与成对候选分析，不应把过小的数据集用于宣称神经网络泛化能力。

## 代码实现约束

- **一切变换必须可复现。** 明确记录 Pass Pipeline 与所有参数，并优先使用已存在且可验证的变换。
- **正确性检查必须独立。** 对数值结果设定合理容忍度并说明原因；非法或超时的候选不能进入有效性能排名。
- **记录失败，不制造结果。** 编译、翻译、执行、校验、计时分别有清晰状态码/异常内容。
- **同等条件比较。** 固定输入、类型、目标 CPU、线程数及运行条件；随机化候选测量次序，报告计时波动。
- **保留可扩展边界。** 编译器适配、工作负载、硬件元信息、测量工具互相解耦，但不为了抽象而引入复杂插件系统。
- **小提交与简明文档。** 每个 milestone 产生可审阅的代码、命令、测试和结果说明。项目文档保持对真实实现的同步。
- **不预设架构。** Phase 0 不训练 Transformer、强化学习或大型图模型，也不开发硬件专用内核。

## 首个可直接执行的开发任务

> 阅读两份研究文档 → 探测环境并记录实际 MLIR / LLVM CLI → 选择一段最小 MLIR 程序跑通 lowering / native 生成 → 保存 2–3 个阶段的 IR 快照 → 编写参考正确性检查与重复计时 → 输出单条 JSONL 轨迹 → 加 Smoke Test 和复现命令 → 提交 M0。
>
> **M0 不需要用户额外确认才开始。** 如果宿主机没有 MLIR 可用或无法完成编译，把准确阻塞点和可执行安装/配置方案提交到文档，不要虚构已成功的性能测试。

## 阶段验收与后续决策

M0 验收一条真实可复现的编译—执行数据闭环；M1 验收多个合法候选在同一测量规范下可比较；M2 验收三种计算类别与明确的实验限制；M3 验收有噪声与正确性分析支撑的研究结论。我们最终决定是否设计 Persistent IR State，取决于这些证据，而不是是否能实现一个 Attention 模块。
