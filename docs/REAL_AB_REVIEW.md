# R4 决策审查：真实程序 A/B 的结论与最后一项 PGO 基线

**日期：2026-10-20。** 本文件审查已完成的 Zstd/SQLite A/B，不修改原正式报告。依据：`experiments/reports/real-zstd-inline-ab.md`、`real-sqlite-pgo-ab.md`、`docs/REAL_AB_PROTOCOL.md` 和工具记录。本审查没有在实验主机重新运行。

## 1. 两个候选的科学结论

### Zstd

在 Zstd 1.5.7 的 `ZSTD_buildSeqStore` 三个源码调用位置，`always_inline` 的后端记录和实际代码均显示内联生效；PGO+ThinLTO 的压缩吞吐相对原实现，在两种语料、两个批次均观察到约 +0.7% 至 +1.0%。无 PGO 时收益方向跨批改变；解压没有同方向稳定加速。PGO 下文本段增加 2368 字节、约 0.32%。原始/noinline 仍保留三个调用，波动中的差别说明布局和系统状态也参与性能变化。

**该实验已达到预先定义的停止点。** 它证明某个编译器的默认内联决定未必是这两类评测输入的最佳实现，但尚未证明跨模块联合优化必要性、全局代码预算需要神经网络协调、或任意新算法的收益。目标 helper 与直接 caller 属于同一 TU，不应宣传为“修复跨 TU 内联”。

### SQLite

P0 使用 `orm,cte`，P1 用预先冻结的索引点查询训练，均约 60 CPU 秒的 Clang instrumentation PGO。P1 在全新点查询负载中约快 4.4–5.4%，范围查询约快 1.9–2.1%（完整进程的同轮配对结果）。训练覆盖从目标调用语句零命中变成明显热路径，最终 text 段约减少 9.5%。但是目标几个调用点**两组均没有被内联**；实际性能改善不能简单归因于更好的单边内联决策。

**该结果主要说明常规 PGO 对输入分布很敏感，而且自身已经能够利用更合适的训练覆盖。** P1 只在类似索引类的新测试中验证，不知道是否牺牲 ORM/CTE 和其它 workload。第二轮存在系统时间漂移和 range 离群值。不能把这次观测当作通用神经编译器的改进幅度。

## 2. 仅建议一个有明确停止条件的后续对照

**目标：** 判断不同 PGO 训练分布是否存在需要程序级协同处理的明显性能权衡，以及传统 LLVM 工具是否已经足以处理。

首先，保持同版本 SQLite 与 Clang/LLD 18.1.3，相同 native + ThinLTO 优化配置，仅改变训练 Profile。建立三个主要配置：

- `P0`：既有 `orm,cte` 训练；
- `P1`：既有索引训练；
- `Pmix`：将两类兼容的 Clang instrumentation PGO Profile 用 `llvm-profdata merge` 合并，必要时使用 `-weighted-input` 来控制两种负载的相对权重。

官方 LLVM 文档支持 profile 加权合并：https://llvm.org/docs/CommandGuide/llvm-profdata.html ，但**合并时统计计数默认按原始命中量累加，不会自动按两个 profile 的训练 CPU 时间归一化**。Agent 先核实本机 LLVM 18 参数与实际 profile 兼容性，记录两类总计数及权重形成理由。避免事后依照最终测试表现挑选权重。

比较时须区分：已有 P0/P1 是既成的诊断性结果；新增 Pmix 若用于科学对照，需要从确定的冻结规范出发建立独立评估。不允许把已观察过的 point/range 当作新的 blind。至少应包含点查、范围查、ORM/CTE（或 main）等不同查询家族，并预先定义一个未用来定权的评估集。若无法实现有效 holdout，则只报告诊断性比较，不能宣称泛化。针对 Pmix 需要明确训练数据获取/合并成本；如果复用 P0/P1 两份各60 CPU秒的 profile，要如实记为120秒历史训练数据，不能冒充60秒同预算；需要同预算结论时重新按总 CPU 时间约束分配训练工作量。

**主要比较量**：各负载延迟、按预设工作负载权重的几何均值、最差负载退化、代码大小和编译/训练开销。保留每轮原始样本，交错测量与跨批复测，且仍需承认 SMT sibling、频率、邻核干扰不受控。不能仅因某个结果更快就宣称存在全局神经优化空间。

**硬停止条件**：若简单加权/合并 PGO 在预设混合工作负载下接近 Pareto 前沿，或者各种差异主要反映训练分布而非编译器决策能力，就结束 SQLite 的进一步局部试验。不得再无限拓展权重/Shape/单边属性组合以寻找偶然的加速。

## 3. 对 IRLoom 总体路线的判断

目前的 R1–R3 和两个 A/B 已充分证明：大型真实应用、PGO 和 LLVM 跨函数编译确实存在上下文/训练分布敏感性，但也表明 **LLVM 的成熟基线已经很强**。这批工作尚未识别出一种必须用 MLIR+Attention 才能解决的残留全局优化问题。

不要把“收集更多性能数据”“自动调 PGO 权重”“逐调用点 always_inline”直接当成我们最初的架构创新。下一次主要科研设计讨论应聚焦一个真正的全局决策对象：例如**多个调用点共享全局代码大小/指令缓存预算，且内联/代码布局/跨函数导入之间存在可重复的交互**。要先取得可操作的合法优化动作和相互作用证据，再判断需不需要可持续的分层程序表示、跨级 Attention 与硬件反馈。

本阶段建议只交付简短的 SQLite `Pmix` 正式/诊断报告和上述停止判断；Zstd 现有 A/B 归档完成，不再自动创建新的单函数实验。保留既有缓存、独立正确性验证、全部失败日志和“不计算产物 hash、不新增单元测试”的项目约定。
