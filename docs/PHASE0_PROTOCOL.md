# Phase 0：跨层级优化数据与性能证据实验协议

本协议是 IRLoom 第一阶段的执行依据。目标是**生成可复现的优化轨迹和真实性能证据**，不是立即证明神经网络优越，也不是开发一个新编译器。

## 1. 核心实验问题

1. 固定原始程序、硬件和工具链，合法优化路径之间的最终执行性能是否存在超出测量噪声的差距？
2. 中途 IR、早期 IR、合法变换历史能否建立可靠的跨层级样本关联？
3. 在某一既定编译决策点，额外提供历史信息是否改善最终性能排序或有限预算内的候选选择？

实验同时保留正、负结果。**Phase 0 的成功标准是采集链路可信和问题可检验，而不是必须观察到速度提升。**

## 2. 初始环境与可迁移性

先在一台方便控制、能直接运行本地可执行文件的 CPU 上建立最短路径：MLIR → LLVM IR → native executable。实验记录实际体系结构、CPU 型号、编译器构建版本、CPU/内存配置、ISA 特征、优化参数和完整命令行，不在实现中写死 x86、ARM、RISC-V 等目标。

由 Agent 自行确认当前安装版本可用的 MLIR Pass/CLI，再确定准确 Pipeline。MLIR Pass 名称和前后依赖随版本变化，**禁止先按网上的旧示例硬编码一条无法跑通的 Pipeline**。优先选择官方已有工具和 Pass：`mlir-opt`、`mlir-translate`、`clang`、`llc` 等。部署依赖应最小化，并保留工具链版本和构建来源。

硬件信息分两类保存：能够静态获取的机器能力（如 ISA、Cache 层级/容量、核数、向量长度）和可选的运行时观测（如 PMU、实际内存带宽）。如果权限不足，记录不可用，不阻止基准运行；不要把“峰值带宽”冒充“该工作负载可达到的带宽”。

## 3. 工作负载与候选搜索空间

先选择三种不同计算性质的样例，每种至少两个规模：

| 类别 | 推荐示例 | 观察重点 |
| --- | --- | --- |
| 计算密集 | Dense matmul 或 matmul + elementwise | 分块、融合、向量化及寄存器压力 |
| 归约 | row/column reduction | 依赖、循环顺序、并行与向量化 |
| 访存/复用 | 2D stencil 或相邻窗口计算 | 数据复用、访存模式、融合与循环变换 |

样例应保持简单、可独立校验，并且真正走 MLIR 多级 Lowering。不要只测 GEMM，也不要一开始引入几十种模型和动态 Shape。选择公开、无需私人数据的程序和固定生成种子。

对每个样例尝试至少四条**有实际差异且被工具链支持的合法候选路径**。优先选择与目标工作负载相关的内建优化：例如不同可支持的 Tiling、循环变换、向量化和融合组合。找不到四条合法路径时，记录阻塞原因并调整样例或可用变换；不得伪造“优化路径”。

保证所有候选的数值语义和 ABI 相符。浮点归约/融合可能改变结合顺序，应明确使用的 fast-math/重关联规则，并按精度规定容忍度，不能默认位级等价。

## 4. 必须采集的编译轨迹

每个候选至少保存以下数据：

1. 原始程序标识、输入规格与生成种子、数据类型、正确性基线。
2. 有序变换事件：所处阶段、Pass/Transform 名称、参数、执行是否成功及错误信息。
3. 编译边界的 IR 快照：高层输入、关键中间层（如循环或 Vector 形式）、LLVM IR。阶段名称以实际可用工具链为准，允许某项缺失但必须注明原因。
4. 源文件、IR、目标代码/可执行文件的 SHA-256 指纹及必要的产物路径；完整构建命令、环境变量和工具链版本。
5. 正确性结果、编译耗时、运行性能样本与设备描述。

最初只需要**快照级 lineage**：每个 `snapshot` 明确来自哪个上游快照、经过哪些变换。不要在 Phase 0 承诺对每个 MLIR Operation 做 1:N/N:M 精确溯源；这属于之后的架构研究。

建议保留原始日志以及结构化 JSONL 清单。示意 schema（字段名可小幅调整，但必须写入实际版本化规范）：

```json
{
  "schema_version": 1,
  "program_id": "matmul",
  "case_id": "matmul-f32-128",
  "candidate_id": "matmul-f32-128-variant-01",
  "seed": 1,
  "input": {"shape": [128, 128, 128], "dtype": "f32"},
  "target": {"arch": "captured", "cpu": "captured", "features": {}},
  "toolchain": {"mlir_version": "captured", "llvm_version": "captured"},
  "pipeline": [{"stage": "high", "action": "recorded", "args": {}}],
  "snapshots": [
    {"stage": "high", "path": "artifacts/.../high.mlir", "sha256": "...", "parent": null}
  ],
  "binary_sha256": "...",
  "correctness": {"status": "pass", "rtol": 0.0001, "atol": 0.0001},
  "compile_seconds": 0.0,
  "timings_ms": [1.02, 1.01, 1.03],
  "status": "ok"
}
```

示例数值只是格式说明。失败样本必须保留 `status`、`error` 和可复现命令，但不能将其作为有效性能样本参与排序。

**同一机器和工具链上、生成完全相同二进制哈希的候选**要在分析中标记为重复实现，避免把无意义的不同 Pass 命名当作不同优化结果。

## 5. 正确性与性能测量

**正确性先于速度。** 每个候选用确定的输入与独立参考实现/已知正确的基线比较；测试边界、非整齐 Shape 和基本数据范围。明示浮点 `rtol`/`atol`、是否允许重关联，以及超时与编译失败的处理方式。生成程序/运行器不能偷偷修改输入规模或绕过计算。

**性能必须测量原生程序。** 把编译耗时与运行耗时分开。对每个候选先预热，再进行至少 10 次计时；报告中位数、分散程度和原始样本。尽可能固定 CPU 亲和性、线程数和运行环境，随机化候选测试顺序，减少温度、频率与系统负载偏差。不可控制的噪声应被记录。可选使用 `perf stat` 或其他硬件计数器；缺权限时保证延迟测量仍能运行。

不要用单次计时、代码长度、推测的指令周期或自造微架构评分充当真实性能收益。若差距和计时波动同一量级，应明确为「尚不能区分」。

## 6. Phase 0 的分析与对照

**A. 路径差异。** 对每个 case 报告各合法候选的正确性、编译开销、运行时间中位数、相对默认 Pipeline 的加速比、不同候选的性能分布和测量波动。确认性能差异是真实的，而不是编译器 Flags、线程设置或执行环境不同造成的。

**B. 跨层级信息价值。** 在一个固定的决策检查点，提取相同预算的简单特征进行离线排名/预测对比：

- B0：只有当前阶段 IR 特征和机器特征；
- B1：B0 + 曾出现过的高层 IR 特征；
- B2：B1 + 有序优化动作历史；
- B3（可选）：将截至当前阶段的全部 IR 快照重新编码，作为“完整历史”对照。

先采用操作计数、循环层次、访问/向量化特征、Shape 和 Pass 参数等透明特征，使用简单线性/树模型，甚至非神经模型。**这些特征只能来自决策时已知的信息**；不许使用未来 LLVM IR、最终二进制指标或真实执行时间预测过去的选择。

按原始程序或程序家族分组拆分训练/验证/测试，避免仅把相同程序的不同 Shape 随机拆分造成泄漏。小样本情况下不要宣称跨工作负载泛化，只报告探索性结果。

**C. 同预算的候选选择。** 在同一候选池内，用各方法选择前 `k` 个候选并进行等预算比较；报告 best-found speedup、best-of-k latency、选中最优候选的概率/排名，以及搜索、编译、模型推理和执行测量的总成本。离线候选池实验必须清晰标注为离线模拟，不得冒充在线优化。

如果 B1/B2 没有带来稳定收益，这依然是重要结论：可检查样本、特征、决策时点，以及历史信息是否早已在当前 IR 中充分体现，之后再决定是否继续做持续神经状态。

## 7. 最小交付与验收

Phase 0 首轮完成时，仓库至少应包含：

- 可运行的环境探测与工具链说明，一条实际成功的 MLIR→本机可执行文件编译路径；
- 三类工作负载、每类两个 Shape（可分批完成，第一条 end-to-end 路径应先交付）；
- 对每个 case 至少四条合法且产生不同变换轨迹的候选（遇到后端限制必须显式说明）；
- 可验证正确性的基准运行器与统一计时协议；
- 机器可读的轨迹数据清单、快照/日志、自动聚合的基础结果；
- 一份简明的 Phase 0 实验报告，明确对照、噪声、正负发现与下一阶段建议。

**验收不是某个固定加速比。** 首先验收可复现性、候选差异、样本质量、变换过程追踪，以及分析是否能够回答研究问题。

## 8. 推荐目录

```text
benchmarks/          # 工作负载、输入与参考结果
compiler/            # 编译 Pipeline、Transform 组合、IR 捕获
profiling/           # 运行测量、机器元数据采集
experiments/         # 配置、数据分析与结果报告
tests/               # 正确性、回归、数据格式验证
artifacts/           # 本地生成的 IR、二进制与日志（不直接大规模提交）
docs/                # 研究协议与结论
```

默认不应将大量生成二进制或逐次 Bench 原始日志推入 Git。提供 `.gitignore` 和小规模示例数据；对于论文实验所需数据，另行定义版本化发布方式。

## 9. 再现性最低要求

每次实验结果应能追溯：`git commit`、操作系统与内核、CPU/机器型号、MLIR/LLVM/Clang 版本、完整 Pass Pipeline、输入种子和 Shape、精度规则、线程/亲和性设置、测量原始值、产物与数据清单哈希。脚本应支持固定配置一键重跑，失败不静默跳过。

执行顺序与首批 Agent 任务见 [AGENT_START.md](AGENT_START.md)。
