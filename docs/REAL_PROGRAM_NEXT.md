# RealBench Phase 1：大型程序优化基线与全局性能机会审计

**状态：2026-10-20；供本地 Agent 执行。** 本方案承接 `docs/REAL_BENCHMARKS.md` 与 `experiments/reports/real-programs-initial.md`。旧的 M0–M7 与 M8 可行性研究文档保留不动。下一步优先在真实程序中寻找优化空间，不立即开发神经网络、MLIR 扩展或完整 LLVM 编译器。

**执行验收：R1–R3已完成。** 14个正式负载/配置组合、140个样本全部通过；两个完整项目的强基线、独立PGO和热点/调用审计见[阶段报告](../experiments/reports/real-programs-baselines.md)。已给出Zstd内联/代码预算与SQLite训练覆盖两个后续问题，最小A/B尚未执行，未验证新的全局优化收益。下面保留原执行规范，不自动扩大到模型或新编译器算法。

## 1. 本轮验收和关键缺口

现有四个项目六项工作负载已完成可复现的源码获取、构建与功能测试；统一入口和外部构建缓存正常。当前 **LLVM/Clang 只编译 LLVMDemangle 小库并以系统 Clang 测一个源文件**，还不是完整编译器作为被优化程序的基线。LLVM test-suite 只运行 7zip/anagram；Zstd 使用重复拼接的源码文本；SQLite `speedtest1 --memdb --size25` 仅约 0.4 秒；每项只有三次独立采样。因此它们可作 smoke baseline，但不能作为“真实大型软件性能优化已被验证”的证据。

IRLoom 的科学目标不是把大型程序的分块参数继续枚举一遍，而是定位已有 **`-O3` / ThinLTO / PGO** 下仍可能存在的跨函数、跨模块、跨编译阶段优化机会。第一步要完成可审计的强基线与热点/调用关系调查。

## 2. 最小正式集合与更有代表性的工作负载

**优先主力：Zstd、SQLite、LLVM test-suite 中的多源程序。** 它们已经具备构建基础，避免额外下载庞大第三方软件。

- **Zstd**：保留旧 8 MiB 源码重复语料作为旧 smoke case，另外选择至少两种**不同数据分布**且可再现的正式语料（例如软件源码包、结构化记录/日志或公开压缩基准语料），规模与来源/生成种子固定。分别统计压缩和解压，至少一个工作负载重复执行时间在秒级；避免用高度重复语料得出通用压缩性能结论。对压缩输出逐字节往返校验。
- **SQLite**：保持 speedtest1 与数据库正确性验证；增加 `--size` 或选择工具实际支持的其它 testset，使运行进入数秒量级。区分内存数据库（CPU/执行引擎）和必要时的文件/磁盘模式（不能混为一个指标）。注意 SQLite amalgamation 经常是单 TU，**ThinLTO 对它可能几乎没有额外跨模块优化空间**，不应以此否定跨模块方法。
- **LLVM test-suite**：从官方固定版本 MultiSource 中优先试跑 `7zip`、`mafft`、`tramp3d-v4`、`Bullet`，可选 `ASCI_Purple`。这些目录已经在官方锁定版本的 `MultiSource/Benchmarks` 下核实存在，但实际 CMake target、依赖和参考输出应由 Agent 在本机核实，避免写死不存在的 target。优先选其中 2–4 项能够独立执行与验证、持续时间足够的真实多源测试。保持官方参考输出或校验程序。
- **LLVM/Clang**：已下载源码保留；`LLVMDemangle` 和编译单 TU 继续标记为环境/工具能力检查。只有在明确估计磁盘/内存/构建成本后，才另建一个可复用的**真正 LLVM/Clang 程序构建目标**，使被优化的是 Clang 程序自身，而非只是让系统 Clang 编译一个源文件。本轮不强制全量 bootstrap，也不允许把现有 Clang TU 编译时间当作我们的新编译器优化成果。

项目首次接入时优先解决固定输入、独立正确性、可再现运行，再扩大测量次数。不要同时引入十余种项目。

## 3. 强编译优化基线

在至少两个可运行的真实项目上，以**相同源码、功能选项、输入和目标机器**进行隔离构建：

1. `O3`：已有 `-O3` 的可移植基线（与旧测试兼容）；
2. `O3-native`：`-O3 -march=native`，作为该 CPU 上更强的常规静态基线；
3. `ThinLTO-native`：在相同 native 基线上启用 `-flto=thin`、LLD；
4. `PGO+ThinLTO-native`：使用 Clang instrumentation PGO，独立执行训练负载、合并 profile，重新构建 PGO+ThinLTO，再以**未参与 profile 采集的评估输入**测试。

至少保证 `O3-native` 与 `ThinLTO-native` 两组真实完整程序构建；PGO 能在同一程序完成闭环时再给出其性能结果。**能力探针的 ThinLTO / PGO 成功不能冒充完整项目结果**。按项目+版本+toolchain+flags+变体隔离缓存；PGO 训练的编译和运行时间、profile merge、重建时间必须计费。保持所有训练/评测文件和编译输出路径隔离，避免旧 profile 或二进制的误用。

原则上以完整 native 程序的真实性能指标为主，`-O3` 与 `-O3-native` 结果不要混用。保存 compile/link 全命令、编译耗时、可执行代码大小、正确性、原始运行样本以及机器环境。

## 4. 性能测量与热点剖析

每项正式工作负载先做一次预热与至少 **10 次独立测量**，顺序交错不同构建变体；记录 median、MAD 和波动情况。需要对短测试加大输入/迭代次数到秒级，并区分进程启动时间、工具自身汇报的计算时间和真实应用吞吐。频率、SMT sibling、邻核干扰与系统缓存不可控的部分必须记录，不要声称已隔离。

在至少两个代表性工作负载上采集**热点函数和调用图相关的 Profiling**（优先 `perf record` / `perf report` / `perf stat`，没有权限时记录限制并用 PGO 函数计数、LLVM 优化记录或可用的静态分析作为替代）。可选从优化记录/ThinLTO 摘要中观察内联决策、跨模块导入、函数大小或代码布局变化，但不得将“看到某个热点”自动推断为“存在编译器错过的优化”。

从实际程序出发，至少找出一到两个**具体可复核的候选研究问题**：例如某组热点调用边上的内联选择与指令缓存/代码大小权衡，或全程序反馈对跨模块优化的影响。明确它们是否已被 PGO/ThinLTO 处理、是否可以构造合法的 A/B 编译对照，以及理论上为何需要超越局部启发式的全局信息。没有发现明确机会，就如实报告负结果，不为了下一个里程碑硬塞 Attention。

## 5. 执行顺序与验收

**R1（工作负载真实性）**：新增具有实际性能意义的 Zstd/SQLite 输入，增加 2–4 个可正确运行的官方 MultiSource 测试。输出每个真实负载的计算类型、时间尺度、函数/源码规模和参考校验。旧 smoke 工作负载保留但单独标记。

**R2（强基线）**：在至少两个真实程序上完成 O3-native vs ThinLTO-native 的功能与性能对照；选择其中一个完成正式独立训练/评测输入的 PGO+ThinLTO 尝试。输出编译/链接/PGO 训练成本与真实性能对照，不要求所有变体必须加速。

**R3（优化机会审计）**：分析至少两项实际程序的热点、函数依赖和优化记录，形成一份有证据的“现有编译器仍可能漏掉的全局优化机会”清单，并给出下一次最小可验证 A/B 实验。

每完成一步提交必要代码/配置、更新 `docs/REAL_BENCHMARKS.md` 和报告，保持源码与二进制仍在外部缓存，使用统一入口。建议最终报告路径 `experiments/reports/real-programs-baselines.md`。不要覆盖初始环境验收报告；继续遵守项目既有的不计算产物 hash、不新增单元测试约定，同时**必须保留真实功能正确性和失败日志**。

**最终验收是：至少两个真实项目具有可信的强编译基线，并找出有充分证据值得研究的跨函数/跨阶段优化决策。** 这一轮不是神经模型训练阶段，也不因某个 benchmark 没有加速就宣称研究失败。
