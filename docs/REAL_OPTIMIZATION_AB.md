# Real-program A/B：从热点证据到可验证的全局优化机会

**状态：2026-10-20；供本地 Agent 执行。** 基于 R1–R3 的真实程序结果和编译优化记录。这里提出的是**最小因果验证**，不是新学习模型的部署计划，也不是已经证实的优化收益。

## 审查结论

R1–R3 已建立 Zstd、SQLite 四种完整编译变体、两项 LLVM MultiSource 参考、140 次正式进程测量以及热点调用记录。Zstd 在当前评测语料上，ThinLTO 相对 O3-native 的额外提升非常有限；SQLite `pgo-thinlto-native` 的 `speedtest1 main` 约 4.263 秒，对应 `o3-native` 的 4.659 秒，报告的速度收益约 9.3%，对 `thinlto-native` 4.599 秒则约快 7.9%。这些是单机单次测量活动的观察，不等于新优化算法已提升 9.3%。

有两个比“扫描所有 Pass / 随机优化配置”更具体的可能性：Zstd 的真实压缩热点存在跨 TU 的较大内联候选，LLVM 的优化记录判定 TooCostly；SQLite 的动态热点路径与预设 `orm,cte` PGO 训练分布有覆盖差异，某些高频调用边在训练 profile 中并不热。必须通过严格 A/B 验证，而非仅凭 gprof/remarks 认定编译器漏优化。

本次建议将 **Zstd 内联 A/B 作为最先执行的一项**，SQLite PGO 覆盖为随后独立的较小实验。不要同时拓展到新的大型项目或全 LLVM bootstrap。

## A. Zstd：热调用链中的内联选择是否存在可利用空间

固定 Zstd 1.5.7、两种已验收的评测语料、`-O3 -march=native -flto=thin` 与相同的 Clang/LLD 18.1.3。报告已有链条 `compressBlock_internal → buildSeqStore → doubleFast`，以及 PGO+ThinLTO 下 `buildSeqStore` 被判 TooCostly 的记录（例如 cost 630 vs threshold 625）；但 buildSeqStore 的自采样很低，调用次数不是性能增益证据。 **源码确认 `ZSTD_buildSeqStore` 是 `zstd_compress.c` 中的 `static` 函数，与 `ZSTD_compressBlock_internal` 同处一个翻译单元；本次拟操作的边本身不是跨 TU 内联。** 压缩实现经函数指针分派到其它 TU 中的匹配器，因此这是一个可能影响跨文件调用链的局部内联决策，不能把它直接称为已经验证的跨模块优化。

**最小三个处理组：** 原始函数属性；`always_inline` / `__attribute__((always_inline))`（依源码语法与合法性）；`noinline`。仅在**独立、版本化的源码工作副本/patch**上改变目标函数属性，不直接污染缓存中的原始源码；优先只动一个确切函数，不修改算法、数据布局或 benchmark harness。原函数若因内联约束失败，保留真实诊断和记录，不伪造“已强制生效”。

实现顺序：

1. 在基线的 `-O3-native`、`ThinLTO-native` 和 `PGO+ThinLTO-native` 的最终优化记录和函数/调用图中定位目标调用边。**确认哪个调用点真正存在于后端优化结果中**，防止优化记录指向不同的 Clone 或已内联上下文。
2. 用最小 patch 建立 3 个独立构建产物，检查源改动只影响函数属性，保存最终 LTO 记录、必要函数汇编片段、代码大小、编译/链接时间；记录三处或其它被影响调用点是否真正发生内联，不凭 `always_inline` 标签推断其成功。
3. 如果采用 Clang instrumentation PGO，针对源码/函数属性变化给**每个变体**以相同、预先冻结的训练语料及训练预算重新采集兼容的 `.profdata`，而不是偷用一个可能产生 CFG / counter 错位的旧 profile。PGO 生成、合并与应用的全部时间要记录。
4. 使用已固定的 `software-eval` 和 `records-eval`，交错测量每变体压缩/解压性能至少 10 次；复核字节级往返和必要的应用输出语义。确认训练和评测输入没有重合。
5. **只以完整程序实际吞吐和真实时间/代码成本判断**。若强制内联使压缩性能下降，或者收益与波动同量级，就把这个热点作为被验证的负结果。不要继续无限挖另外几十个函数；先总结再选新的研究命题。

对 Zstd，压缩与解压分别报告，不能把两者平均后掩盖一个方向退化。关注总 text、热点代码体积、编译与 PGO 训练成本的权衡；gprof 1% 或内联 remark 的 cost 差异本身不是性能结论。

## B. SQLite：PGO 训练分布是否导致可修正的热点错误决策

此项先进行“**评测调用点 → 源码/IR/最终代码 → 训练覆盖**”对应审计。当前 `VdbeExec → BtreeIndexMoveto` 总计约 330 万动态调用，但不能将整条函数调用累计数误对应到一个 `Hotness=0` 的 inliner remark。SQLite 核心通常是 amalgamation 单 TU，缺少跨模块可见性不是已发现的问题。

在同一源码、Clang/LLD、`-O3 -march=native` + ThinLTO 下冻结两种**同等训练执行预算**的 PGO 配方：
- P0：已实现的 `orm,cte` 训练；
- P1：使用 speedtest1 官方支持的索引/查询密集 testset 或可审计 SQL workload，提前冻结输入及种子以覆盖目标调用类型。先通过本机帮助和源码确认 testset 合法，不假设名称一定可用。

评估集必须另选预先冻结、**没有参与任一训练的工作负载/输入**。旧 `main` 已在前次诊断中被观察，可以作为辅助但不能再冒充全新 blind。以相同功能、构建标志、输出正确性条件对比 P0/P1 的总执行性能、编译优化记录、profile 覆盖和代码体积；按前述十轮交错和必要跨批复现。尤其要报告 P1 是否只是过拟合一种查询而牺牲别的场景。

**停止条件：** 如果训练覆盖完善后收益已被常规 PGO 捕获，这是训练数据设计问题，不能声明需要一个新的全局神经编译架构。只有传统 PGO 仍未充分解决的调用决策，在受控属性/编译策略 A/B 中显示持续收益，才继续寻找更广泛的联合决策规律。

## C. 从这两个 A/B 提炼研究问题的条件

不要因为单个函数强制内联快了几百分点，就立即构建 Attention。至少需要看到：

1. **非平凡的决策交互**：改变调用方上下文、热点分布、代码体积或硬件约束，最优选择出现稳定差异，而不是对某个函数永远选择 inline；
2. **传统基线无法廉价完全解决**：已比较现有 `-O3 / ThinLTO / PGO` 和合理启发式，剩余空间不能简单归因于较差训练数据；
3. **可扩展的优化对象**：在至少多个真实函数调用边、多个程序或多种负载中出现共性，并且能构造合法的优化动作集合；
4. **决策可学习且有价值**：输入表示（跨函数/跨阶段/硬件信息）帮助选出真实更快代码，成本计入全部编译、特征提取与实际 Profiling。

届时才比较本地启发式、完整调用图统计与分层稀疏 Attention/持续状态架构。不能以单个热点 A/B 的小收益证明大模型架构必要性。

## D. Agent 的本轮任务与交付

先完成 **Zstd A/B**，输出独立构建产物、完全可复现的patch、编译优化记录和相对强基线的正式性能结论，汇报文件建议为 `experiments/reports/real-zstd-inline-ab.md`。请先不扩大其它 Benchmark，也不改动已有 R1–R3 数据/报告。

所有候选正确性检查、性能原始样本、命令、产物隔离必须保留；不得覆盖旧报告，不能省略训练集与评测集隔离。沿用项目既有的不计算产物 hash、不新增单元测试约定。优先完整闭环和研究价值，不进行大规模神经训练或源码重构。
